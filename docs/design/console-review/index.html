APPCALL DASHBOARD REVIEW · 13 Sep 2026 appcall is two surfaces acting as one product: an Apps layer (connectors, connections, calls, syncs, events; the Pipedream / Composio / Merge.dev shape) and a Workflows layer (the Temporal-like durable engine: runs, history, retries, signals, reconciliation). Today the dashboard shows only the first; the engine is a standalone crate with its own transport (start run, history, signals, cancel, resume, reconcile) and no presence in the console, while the word 'Runs' is spent on the sync queue. A user cannot learn that the second surface exists, let alone when to reach for it. What holds up: the Signal system (ink ramp, iris accent, Archivo + Plex Mono, 4px controls, rule-plus-word status, honest 'not recorded' values, a11y). Keep all of it. The gap is that the product exposes machinery before value. The five things that matter most: 1. Name both surfaces at the top level. Rail becomes APPS (Connectors · Connections · Calls · Syncs · Events) and WORKFLOWS (Workflows · Runs). 'Start here' teaches the choice in one screen; Overview shows both halves. 2. There is no way to get an API key. Settings says 'managed via the API' but nothing mints one. First run + Settings › API keys fix that. 3. IDs where names belong. 'Run as' lists conn_… IDs; Connections says 'Provider identity not recorded' on every row. Identity is the label, the ID is copyable. 4. Everything advanced is on the surface (eight filter fields on Logs, six tiles on Runs, credential + JSON on every run form). One search, one segment, a time range; the rest behind 'More filters' / 'Advanced'. 5. Two defects on the first screen a new user sees: the primary 'Browse connectors' button renders iris text on an ink-50 fill (overview.rs: .overview-activation a overrides the button) and looks disabled; 'Run health unavailable.' hangs as an orphan line. Also: the empty request-result box on Connectors renders as a visible bordered rectangle. Renames proposed here: Logs → Calls, Runs (sync queue) → Syncs, so 'Runs' can mean workflow runs. Events and Usage keep their pages; not redrawn.

START HERE (new)
The one screen that answers 'which do I need'. Two equal cards, same anatomy: what it is, use it when, you get, first step.

3 The rule of thumb and one worked example tie the two together: a workflow is steps that are app calls.
Copy is grounded in engine types: retries, timers, signals, child runs, reconciliation.

OVERVIEW
Two halves, same words as the rail.

Workflows · list and runs

screens/09-workflows-list.html · 1440×820

WORKFLOWS (new)
The engine's first console. Nothing here is a builder: workflows are registered from code, the page shows what is registered and what is running.
1 'How to register one' is the only call to action; it opens docs.
2 Runs table leads with the engine state and 'where it is' in plain words (waiting on which signal, which activity is retrying, what is missing).
3 'Needs you' groups the four states a person must resolve. Every other state resolves itself.
Backed by the engine transport: POST /runs, GET /runs/{id}, /history, /reconciliation; POST /signals, /cancel, /resume, /reconcile.

WORKFLOWS · RUN DETAIL (new)
